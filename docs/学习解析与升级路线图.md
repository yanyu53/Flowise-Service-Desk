# Flowise-plus：学习解析与升级路线图

本目录用于你在 `Flowise-plus/`（复刻版）中学习、拆解并逐步改造成**自己的项目**。原则是：先跑起来、再理解清楚、最后再做可控升级（小步快跑、随时可回滚）。

## 1. 项目结构速览（monorepo）

根目录使用 **pnpm workspaces + turbo** 管理多包构建。

- `packages/server`: Node 后端（API/运行时/数据层/队列等）
- `packages/ui`: 前端（React/Vite，开发模式默认在 8080）
- `packages/components`: 节点/第三方集成（可理解为“可插拔能力”）
- `api-documentation`: swagger-ui（由 express 自动生成的文档）

常用命令（在 `Flowise-plus/` 根目录执行）：

- `pnpm install`
- `pnpm build`
- `pnpm dev`（开发联调）
- `pnpm start`（生产启动）

## 2. 你要“改成自己的项目”，建议先做的三件事

- **品牌与包名隔离**：已把根 `package.json` 的 `name` 改为 `flowise-plus`，避免后续你发布/二开时跟上游混淆。
- **配置集中化**：把后端的 `.env`/配置读取做成“单入口”（例如 `packages/server/src/config/*`），并给出校验、默认值、以及运行时打印关键配置（脱敏）。
- **二开边界清晰化**：新增 `docs/` 记录“你改了什么、为什么改、如何升级上游代码时不冲突”。

## 3. 升级方向（我建议的“值得做”的升级）

下面每项都尽量是**可分阶段落地**、并且能明显提升你作为“自己的产品”的可维护性与可运营性。

### 3.1 企业化能力（优先级高）

- **登录鉴权 + RBAC**：支持用户/角色/权限；对关键 API 加鉴权；UI 根据权限隐藏/禁用操作。
- **多租户（Tenant/Workspace）**：把数据隔离做成一等公民（同库不同 tenant_id 或不同 schema），避免后期返工。
- **审计日志**：记录谁在何时做了什么（创建/修改/发布/运行工作流），支持检索与导出。

### 3.2 稳定性与可观测性（优先级高）

- **请求链路与日志规范**：统一 requestId/traceId；结构化日志（JSON）；日志脱敏。
- **指标与健康检查**：细化 `/healthz`、`/readyz`；关键依赖（DB/向量库/队列）探活；关键指标（请求耗时、失败率、队列堆积、模型调用耗时）。
- **更明确的错误模型**：后端 error code 体系 + UI 友好提示；对上游 SDK 错误做归类（重试/不重试）。

### 3.3 插件化（让二开更轻松）

- **“节点包/连接器”注册机制**：把你自定义节点放在独立包（例如 `packages/extensions-*`），通过注册表/manifest 自动发现。
- **权限与配置沙箱**：对插件需要的 env/权限做声明（manifest），部署时可控放行。

### 3.4 研发体验（长期收益）

- **端到端测试**（Playwright）覆盖最关键路径：登录（若做）、创建工作流、运行一次、查看日志/输出。
- **CI**：lint + test + build；PR 校验；依赖安全扫描。
- **代码规范**：更细粒度的 lint 规则与 commit 约束（可选）。

## 4. 推荐的落地顺序（不会把自己绕死）

我建议你按以下顺序做（每一步都能独立交付）：

1) 跑通开发与生产启动流程（本地 + docker）
2) 配置集中化 + 运行时诊断（`pnpm doctor` 之类的自检）
3) API 错误模型统一（后端）+ UI 错误提示统一
4) 鉴权/RBAC（先保护写操作，再逐步全覆盖）
5) 多租户（有了 RBAC 再做更稳）
6) 可观测性（指标/日志/trace）
7) 插件化 + 自定义节点包
